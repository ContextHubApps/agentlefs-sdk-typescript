# ContextHub TypeScript SDK

Official TypeScript client for the ContextHub REST API.

> **Not published yet.** This repo exists so SDK generation has a home. It has no
> installable package on npm, and the sections below describe where things are headed
> rather than what you can run today. See [Status](#status).

---

## Status

| | |
|---|---|
| Package | not yet published |
| Repo visibility | private, until there is something worth installing |
| Generated by | [Stainless](https://www.stainless.com) (pending setup) |
| Source of truth | `openapi/v1.yaml` in the ContextHub API repo |
| API surface it will cover | documents, folders, renames, moves, search, grants |

Going public is a prerequisite for npm publishing and is a deliberate later step, not an
oversight: an installable package that points at a server which does not resolve is worse
than no package.

Blockers before a first generation is worth publishing, tracked in the API repo:

- **Operation names.** The spec has no `operationId` on any of its 14 operations, and
  Stainless derives method names from them. Generating now would mean living with
  invented names in a published package.
- **Server URL.** The spec's primary server does not currently resolve. An SDK that
  ships pointing at a dead host is worse than no SDK.
- **Named response schemas.** Several responses are inline, which become anonymous
  generated types rather than types a customer can import by name.

## This code will be generated

Once generation is wired up, **the entire source tree here is written by Stainless**
from the OpenAPI spec, and it force-pushes on each regeneration.

That has one consequence worth stating plainly, because it is the mistake this README
exists to prevent:

**Do not hand-edit generated files.** A fix belongs in one of two places:

1. **The OpenAPI spec** (`openapi/v1.yaml` in the API repo), if the API's shape or
   documentation is wrong. This is where most SDK problems actually live.
2. **The Stainless config**, if the API is right but the generated ergonomics are not
   (method naming, pagination handling, resource grouping).

Anything edited directly in this repo is lost on the next generation, silently.

## What the SDK will handle for you

The API is deliberately explicit about a few things so that application code gets
predictable behaviour. The SDK's job is to make those correct by default rather than
leave them to each caller:

| API requirement | What the SDK does with it |
|---|---|
| `Idempotency-Key` on creates | generated per request, so a retry cannot duplicate |
| `If-Match` on updates and deletes | round-trips the `ETag` from a read |
| Cursor pagination | exposed as an async iterator, no manual cursor threading |
| Typed error codes | thrown as distinct error classes, not string matching |

## One thing to understand before integrating

**A `404` does not mean you got the path wrong.**

If your API key is not permitted to read something, the API returns `404` with exactly
the response it would give for something that does not exist. The two are
byte-identical, on purpose: if they differed, any key holder could map content they
cannot read by watching which paths answer differently.

So there is no `403` anywhere on this API and no error meaning "forbidden". A
surprising `404` is a question about **grants**, not about your path.
